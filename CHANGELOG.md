# CHANGELOG

## [Unreleased]

### Added

- The event detail page is rebuilt around a hero and a sticky right column. Guests and attendees now land on a two-column hero — cover image beside the title, the date, time, duration, venue and speaker facts, a register button and a live countdown — then a 65/35 layout: the left column holds the about card, a public course-schedule timeline and speaker tiles that open a profile overlay, and the sticky right column carries the register card — Register, or Enter Room once a ticket and linked course are held — with add-to-calendar, Google Maps and share controls beneath it. The schedule and speaker facts are public, so the whole page works signed out; a signed-out Register still routes through sign-up with a redirect back, and staff are still sent to their event page.

- Speakers and staff now get the same account treatment as everyone else. Their top bar holds the brand and the profile menu — the user picture, name, **User settings** and **Sign out** — and the side navbar becomes a slim icon rail that expands to show the link labels when hovered or focused, overlaying the page rather than shifting it. The nav links themselves are unchanged, so a role's links still come from the same shared source as the attendee top bar.

- Attendees and guests now get a top navbar instead of the side navbar. The header runs the full width at every breakpoint — no hamburger, no `lg:` hiding — with the brand, Home/Events/Community (plus Tickets for attendees), and the signed-in profile (name and picture) top-right expanding into **User settings** and **Sign out**, or SIGN IN / SIGN UP for guests. Speakers and staff keep the side navbar unchanged. The two layouts read from one shared source of truth for nav items and profile rendering, so a role's links and the profile chip stay consistent wherever they render.

- Staff events now render as a table instead of a card grid, and the event detail page is tabbed rather than one stacked card per event service. Facilitators get a dedicated assigned-events page — draft and active events under Upcoming, finished ones under Completed — while admins keep the full event list with its Drafts tab and reach editing, the cover image, speakers and surveys from separate tabs. Event editing, cover image uploads and post-event surveys are admin-only; a facilitator sees only the Overview, Course and Kiosk tabs and no Publish or Delete controls.

- Post-event surveys can now be emailed to an event's registered attendees. Once an event ends, staff with edit access can opt the event into surveys, preview the form, and send it from the event page; every non-cancelled ticket holder receives a personalized link with a required 1–5 rating and an optional comment. Responses land on the same page as a star breakdown and attributed comments. Sending is a deliberate staff action, not a scheduler: there is no cron, so nothing goes out unless a staff member presses send. Undelivered emails are retried by sending again, and a survey link stops working 14 days after the send — earlier than that it submits at most once per attendee.
- Community groups are now listed on their own page for every visitor, with a management page for staff. The old community links table served a single hidden audience, so it carried platform and event tags that no longer meant anything and its links appeared only where a page chose to hard-code them. The table is reworked around an `is_hidden` flag and a staff-managed ordering: staff can add, edit, hide, reorder and delete group cards, and everyone else — anonymous visitors included — sees the visible ones. Visibility is enforced by row-level security with a role subquery, not by the application, and reads are public while every write is gated to admins and superadmins.

- The event detail page now matches the prototype after a live review. The hero was a bare cover banner with nothing but the title; it is now the two-column cover-and-facts header with the register CTA and countdown. The course-schedule card could silently disappear — a failed or empty schedule fetch removed it entirely, so an event with a course showed no outline at all; the card now always renders and says "No schedule yet." or shows a load error. The add-to-calendar button sat below the countdown behind a divider, which read as part of a separate card; it now sits directly under the register button. A venue that wraps past two lines came out ragged because the value was not constrained; it now right-aligns. The right column scrolled away with the page instead of staying pinned: the shell's scroll area shadowed the browser's, so the sticky element never engaged. Speaker photos never rendered because the event payload carried only a legacy speaker-profile photo column that no longer exists in the schema — it now embeds the speaker's account profile picture, which is where the photos actually live.

### Fixed

- The event detail page review round is closed out. The schedule timeline now frames the modules with the event's own window — Event starts opens the list and Event ends closes it, instead of one combined row — and every time sits to the left of the timeline line with a fixed gap instead of crowding the module names. The add-to-calendar button's icon renders again: the trigger used `calendar_plus`, which is not a Material Symbols glyph, so the browser drew the name as text; it now uses `calendar_add_on`. The location card shows a single map icon rather than two — the header chip only repeated the Google Maps link's icon. The hero's facts panel is now a proper card like the rest of the page, and the Speaker fact moved off it; the Speakers section below already carries the same names.
- The hero is now one card and the schedule card reads like an event schedule. The cover image and the facts panel were two adjacent blocks — the image a bare rounded div, the facts a separate card — so the hero looked split; they now share a single surface with the image flush against it, and the facts column matches the width of the right-hand register and location cards instead of overshooting them. The course-schedule heading renamed itself after the page it lives on ("Event schedule"), and the timeline's times moved from the left gutter to the right edge of the card, where an empty window leaves the module name on the same left-hand line as every other module.
- The register CTA moved off the hero and the room stays shut until the event starts. The hero card carried its own Register Now button beside the register card's, so the page offered the same action twice; the hero now holds the title, facts and countdown, and the register card owns the CTA. Once someone holds a ticket, the register card no longer shows the price, and its button says Enter Room only after the event has started — before that it sits locked, because the room answers nobody from the audience early: the room feed withholds the curriculum from ticket holders until the opening edge passes, so a pre-start attendee gets a lock screen with the event's opening time instead of the course, while staff and assigned speakers keep access to set the room up.
- The event detail page now works for guests end to end. The schedule endpoint was public by design but the middleware never let an anonymous GET through, so the schedule card 401'd for every logged-out visitor (and the two errors in the network tab were the same card fetched twice by dev strict mode). Speaker avatars had the same wall: profile images sat behind the session even though they are rendered on the public page. Schedule GETs and profile-image GETs now pass the middleware, and a profile image is served without a session only when its owner's speaker profile sits on a published event — ordinary account photos stay private, so this does not open the whole `profile_images` bucket. Draft and unknown events answer an empty schedule list rather than a leak of their course. The schedule timeline itself also shows what was already there but hidden: the event's own start and end time lead the list, each module shows its full window when it has one, and an assigned speaker is printed on the module's row instead of hiding behind a click.
- Assigned speakers can moderate their event's Q&A in the room. The course room admitted assigned speakers as course team, but the Q&A panel's delete and lock controls were gated on the facilitator role alone, so an assigned speaker could run a live session with no way to retire a bad question or lock the module once it was over. The control floor now matches the admission rule: admins, facilitators and assigned speakers all get the moderation controls.
- The course room's session timing no longer breaks on times without a seconds part. Event and module times arrive unpadded ("9:00"), which the ISO parse rejects, so the countdown, the session timeline and the live-module status all silently refused to start before the event. Times are now padded before parsing, and a parse failure is a distinct null rather than an Invalid Date.
- A room's ticket and speaker facts are now computed server-side against its exact event. The client previously paged through the caller's own ticket list to decide admission, so a ticket whose row sat beyond the first page could read as not held. The room and event detail routes now answer the caller's live ticket and speaker assignment directly, and the client reads those facts from the one response it already fetches.
- Removing a member from the organization works again for anyone with a history. Every table that records a user's activity — payments, tickets, the audit log, email log, chat and Q&A messages — referenced the account with no delete rule, so deleting a user who had paid for a ticket or left an audit trail was refused by the database and the remove request answered `500`. Those references now release the record instead: the account is deleted, and the payment, ticket, audit, email, chat and Q&A rows it owned are kept with their actor set to unknown.
- Speakers can enter their assigned event room again. The room page read the route's `id` parameter, but the speaker room's route names it `eventId`, so every visit requested `/api/events/undefined` — a 404 — and showed "Access denied." before, during and after the event. The page now reads the parameter it actually has, and an assigned speaker clears the room gate at any point in the event's lifecycle.
- Creating a course for an event that already has one now says so. An event owns at most one course, but the second attempt was reported as a server fault — the create page showed "Failed to create course" and the author had no way to tell a database outage from a rule they had just hit. The refusal is now answered as a conflict, and the create page shows the reason the API gives rather than always substituting its own.
- The dev server no longer crashes with a JavaScript heap out-of-memory error. Turbopack in Next 16.2 kept every compiled route in memory with no eviction, so a session — or a stale `.next/dev/cache` from a long one — grew the `next-server` process past the V8 heap limit within minutes. Next 16.3's memory eviction, on by default, drops idle compiled output to disk: a full route pass now settles around 1.7–2.7GB and reclaims to well under a gigabyte when idle instead of climbing past 9GB.
- Unassigning a speaker from an event no longer leaves their name attached to course modules. Module speaker slots reference a speaker profile whose row outlives the assignment, so removing a speaker from an event previously kept their modules showing them in the builder and in the room's schedule — pointing at someone who could no longer attend. The reference is now cleared in the same request that unassigns them.
- Reordering course modules and lessons no longer relies on drag and drop. Dragging was unavailable to keyboard and touch users, and the drag affordances were easy to trigger by accident while scrolling. Modules and lessons now move with explicit up/down buttons: a module's buttons reorder it among the others, and a lesson's buttons reorder it within its module or, at either end of the module, across into the neighbouring content module — lessons never land in a Q&A module, which has no content of its own. The cross-module move is persisted in the same request, so a course reloads with the lesson in the module it was dropped next to.
- The Q&A module lock control has been removed from the course builder entirely. The lock's only purpose was guarding a staff-facing moderation flow that no longer exists in this interface, so the toggle and its badge no longer appear.
- A ticket email sent to an unresponsive mail server no longer leaks its connection. When the SMTP session timed out, the abandoned session was left parked waiting for a reply that never came, so the socket it held was never closed — and each retry opened another beside it, three per message against a stalled host. Those connections accumulated for the life of the isolate, and because a Workers isolate serves many requests over minutes or hours, a spell of trouble at the mail host degraded every later request that isolate happened to handle. Closing the connection is now the job of the code that opened it, which runs whether the session finishes, fails, or is abandoned to the timeout.
- Server-side database clients are no longer rebuilt for each request. Every one of them started a token-refresh timer that was never stopped, and that timer held the entire client — auth, realtime and query layers together — in memory permanently, so a long-lived isolate accrued one per request until it ran out of room. A single client is now shared across requests with the refresh timer off; it holds no per-user session, so there was never anything to keep apart.
- The course builder's move buttons now say where a lesson will land. Hovering an arrow highlights the exact spot — the row it swaps with inside a module, or a "drops in as the first/last lesson" handle on the neighbouring content module for a crossing move — and every button's accessible label names the destination. A moved lesson briefly glows, and a move across modules announces its new home and scrolls it into view, so a reorder registers even when the target is off-screen. The drop indicator is an overlay rather than a row in the document flow, so hovering an up-arrow no longer shifts the layout beneath the cursor and makes the preview blink between modules.
- The staff nav rail now animates open and closed instead of snapping. Its links toggled `justify-content`, which the browser cannot interpolate, so the icon teleported to the centre the instant the rail began to shrink, and the label's width jumped because `width: auto` is not a transitionable value either. Each icon now lives in a fixed-width box that never moves between the two states, and the label reveals by animating `max-width`, `margin-left` and `opacity` — closing glides and nothing cuts into place. Keyboard focus expands the rail and reveals the labels too.
- The staff nav rail no longer sticks open after you click a link. The clicked link keeps focus across navigation, and the rail expanded on `:focus-within` — which matches any focus, mouse clicks included — so it stayed wide until you clicked somewhere else to move focus. The rail now expands on hover or keyboard focus only (`:focus-visible`), so a mouse-clicked link closes it the moment the pointer leaves.
- Uploading a new profile photo now updates the photo in the account settings page immediately, without a refresh. The upload already wrote the new URL to the database, but only the navbar heard about it — it subscribed to a one-off `profile-photo-updated` event the upload fired — while the settings page read the stale URL from the in-memory session user, so its preview changed only after a reload. The session now accepts an update of its user, the upload writes the new photo URL into it, and every reader — the navbar and the settings page alike — sees it the instant the upload lands. The hand-rolled event is gone, so there is one source of truth for the profile photo instead of two.

### Security

- A lesson link is recognized as a YouTube video only when its host is one. The check asked whether the hostname _contained_ `youtube.com` or `youtu.be`, so `youtube.com.attacker.example` and `youtu.be.attacker.example` passed it, and a lesson pointing at an attacker's host was rendered as an embedded player instead of the labelled external link every other destination gets — hiding where the content actually came from. The hostname is now matched whole against the YouTube domains, and non-HTTP schemes are refused outright.

- A role allowlist no longer admits every signed-in account. The server had one variadic "minimum role" check, so a list like `attendee, facilitator` — meant to admit those two — silently admitted speakers and admins as well, and `facilitator, speaker` admitted every role above attendee. Ticket and payment reads even had to compensate by scoping themselves by entitlement inside the handler, because their guard let everyone through. Staff checks now use an explicit "at least this level" guard, and the few endpoints that genuinely want a specific set — editing a speaker profile — match the role exactly, so a higher role is refused instead of silently allowed.
- Records only their owner or the event's own team may touch can no longer be changed by any staff account. A facilitator or speaker could act on records they had no part in: any speaker could read any course's curriculum and delete any Q&A question, any facilitator could delete any support message, and any facilitator could delete any speaker profile. Those endpoints now check ownership or assignment first — a course or question is reachable only by its event's assigned team, a support message by a participant or the case's assigned facilitator, and a speaker profile by its owner or an admin. Speaker pages also require a sign-in now, and the staff courses page redirects to the access-denied screen instead of rendering a permanently blank page.
- Draft event covers are no longer readable by every signed-in user. Covers are served through `/api/storage/event_images/...`, whose object keys are `events/{id}/cover.png` against sequential ids, so any account could fetch the cover of an unpublished event by guessing the path. Serving one now requires the event to be published, or the facilitator role — the same rule the event listing already applied to drafts.
- Course material is no longer readable by any signed-in user. `/api/storage/[bucket]/[...path]` read any bucket and object key straight from the URL using the service client, bypassing row level security — paid course videos and assets were available to anyone with an account. Access now requires a live ticket to the event teaching the course, a speaker assignment to it, or the facilitator role.
- Storage requests are answered `Cache-Control: private`. Entitlement is per user, and the previous `public` response could be served from a shared cache to someone not entitled to it.
- Uploaded images no longer carry the uploader's location. A phone writes GPS coordinates, its serial and the exact time into every photo it takes, so a profile picture published the uploader's home address to anyone who downloaded the file. Metadata is now removed on the server, in the one place every upload passes through — the browser-side resize strips it too, but only for images it can decode, and a request sent straight to the endpoint never reaches the browser's copy at all. Pixels are untouched: the container's metadata segments are dropped without decoding or re-encoding, so quality and colour profile survive exactly. Which way up the photo goes is carried across on its own — a camera leaves a portrait photo's pixels sideways and records the rotation in the same block as the coordinates, so dropping the block wholesale would stand every portrait photo on its side. Only that one value is rebuilt, into a segment holding nothing else. Nothing new is refused — a file the stripper cannot read is stored as it arrived, since what may be uploaded is the route's judgement rather than the stripper's.
- Facilitators can no longer edit events they do not manage. The event write endpoints trusted the facilitator role alone, so any facilitator could edit or publish any event and read any event's attendee list, and delete — reachable by the event owner's own assistants — could destroy an event they merely helped run. These actions now require an admin or a facilitator assigned to that specific event, and delete is admin-only, the same rule the event rooms already enforced.

### Fixed

- Creating a course from the speaker or staff page works. The create form sent an empty description as `null`, but the API schema accepted only a string or an absent key, so every "Create Course" click was answered `400` and the curriculum builder never appeared. The schema now accepts `null` — the value the DAO already stores. Fixing that surfaced the next gate: the speaker check filtered an embedded table it never selected, which PostgREST answers `PGRST108`, so the query returned nothing and every assigned speaker was `403`ed. The check now resolves the speaker profile and looks the assignment up directly, like the speaker page already did. A failed create no longer fails silently either: the page shows the API error instead of doing nothing.
- Assigning speakers to an event actually saves them. The bulk-assign validation had the same broken embedded filter — it selected only profile ids while filtering on the user's role, so PostgREST answered `PGRST108` and every assignment was silently dropped when an event was created or edited.
- An invitation is no longer accepted by machines. `/invite` redirected straight into Supabase's verification endpoint, and verification spends the single-use token — so a mail scanner, security gateway or link previewer following the address in the message consumed the invitation before the invitee opened it, leaving them a dead link and an address that then counted as registered. Opening the page now does nothing: it offers an Accept button, and only that submission verifies — no scanner submits a form. Acceptance is also handled by the application rather than by a redirect to Supabase, so the token stays in a request body instead of travelling through a URL, and a refresh cannot resubmit it.

- An invitation nobody accepted can be sent again. The invite refused a second attempt for an address Supabase already held an account for, and it holds one from the moment the first invitation is issued — so a facilitator or speaker who never received the mail, or whose link was spent by a mail scanner before they clicked it, could not be invited again by any means. Whether the invitation was accepted is now decided by whether anyone ever signed in with it, and an unaccepted one is replaced by a fresh invitation, carrying whichever role was chosen this time. An address whose owner has signed in is still refused.

- Image uploads work again. Every upload route — event covers, profile photos and course material — failed on the deployed site, because the resizer compiled its WebAssembly while answering the request and the Workers runtime only permits that at startup. No cover image had ever uploaded successfully in production, and the build gave no warning. Images are now shrunk by the browser before they are sent, which removes the WebAssembly rather than working around it: the upload itself is faster, since the smaller file is what crosses the network, and photos taken in portrait are no longer stored on their side. Videos and documents are passed through untouched, and a browser that cannot read the image uploads it unchanged instead of refusing.

- Pages no longer fail outright in the minutes after a deploy. A freshly started isolate spends its CPU budget loading the application before any handler runs, so a page that fans out into many requests at once could exhaust it and return nothing — `/tickets` was the worst, issuing ten server requests for one navigation, and even `/favicon.ico` failed because the project had no icon and each request booted the server to render a 404. The ticket list now arrives complete in a single request and each ticket's QR is drawn by the browser from data it already holds, cover images on `/` and `/events` no longer look up who is asking before serving a published one, and an icon exists. Warm isolates were never affected, which is why this came and went.
- A deployment with no mailbox configured no longer reports mail it never sent. Missing SMTP credentials degraded to the console provider on every runtime, and that provider reports success — so `EMAIL_LOG` recorded `sent`, and an administrator inviting a facilitator or speaker was told the invitation went out while nothing left the isolate. This is how the three `SMTP_*` secrets stayed unset in production unnoticed. On the Workers runtime a missing mailbox is now a failure: the invite answers `502` and the account it half-created is cleaned up so the address can be invited again, and ticket mail records a failed row. `pnpm dev` still logs to the console, where no socket exists either way and nothing is wrong.
- The tickets page renders again. Ticket rows carry their event under `EVENT`, but the card read `EVENTS` and dereferenced it without a guard, so the page threw for anyone actually holding a ticket. The same drift between what the API returns and what the client expected left the payments page showing "Unknown" for every event, ticket cards never showing a paid time, and four list views keyed on columns that do not exist — audit logs, email logs, payments and tickets all key on `id`.
- Assigning a speaker to an event works. The dropdown keyed its options on a column the API does not return, so the submitted value was not a number and every assignment was rejected as invalid. The same missing value meant speakers already on the event were never removed from the list, and every name displayed as "Speaker #undefined".
- Pages no longer sit on a loading spinner that never resolves. `/staff/courses`, the check-in kiosk, payments, checkout, event registration and room access each gated their data fetch on a session flag renamed to its opposite, so the fetch ran only while the session was still loading and was skipped once it was ready.
- The events list no longer flashes "No events found" before the events appear. A superseded request cleared the loading flag while the list was still empty, so the empty state rendered until the live request landed.
- Event cover images load for signed-out visitors. Covers are stored as `/api/storage/...` URLs and the middleware required a session for all of `/api/*`, so every cover on the landing page and the events list was answered `401`.
- Events can be created with a price, venue address, description and currency. The form collected five of the ten columns the API accepts, so every event created through the interface was free — and stayed free, because the edit form was missing the same five fields. A one-sided time range is now rejected in the form rather than arriving as an unexplained failure.
- Signing out no longer reports "Access Denied". Guarded pages treated a missing session as a permission failure, so logging out while on a staff page redirected to the denial screen instead of home.
- Event cards on the home page link to their event. The card read an id field the API does not return, so every link pointed at `/events/undefined`.
- The events listing and event detail pages load for signed-out visitors again. The middleware treated every `/api/*` route as protected, so an anonymous browser's fetch of `/api/events` was answered `401` before the handler ran, even though those handlers were built to serve published events to callers without a session. Public GETs on the event endpoints now pass through, with the handlers still filtering out drafts and every write staying behind the role guards.
- Sessions survive a token refresh. The middleware rebuilt its response once per cookie, so each write discarded the one before it and the browser was left holding part of a chunked auth token — presenting as a random logout. Refusing a request no longer drops the cookies either, which is what cleared an expired session, so a stale token could previously fail the same way on every retry. Responses that carry a refreshed session are now marked uncacheable, since a shared cache could otherwise replay one visitor's session to the next.
- Deleting an event now deletes its course material. Asset and video paths were collected and then discarded: the single cleanup call only ever targeted the `event_images` bucket, so every deleted event left its uploads orphaned in storage.
- Attendee search returns matches again. The filter named embedded columns at the top level, which PostgREST does not apply, so searching a name or email quietly returned nothing. Search terms are now escaped as well — an underscore in an email address matched any character, and a comma silently split the filter.
- QR check-in works again. Every scan returned "Invalid QR token" because the ticket lookup joined the user through the wrong column, so the query errored and the ticket was reported as missing.
- Inviting a member now invites them. The organization invite validated the form, wrote an audit entry and reported success without contacting anybody or creating anything — the invited person was never told, and no account existed for them to use. An invitation now goes out over the same mail server as the ticket emails, and accepting it grants the role they were invited as instead of dropping them in as an attendee. The message is built by the application rather than by Supabase, so it matches the other emails and its link stays on the project's own domain.
- Chat message senders, the event attendee list, and email log recipients load again — all four affected queries shared the same fault.
- Course pages load again. Three modules deleted during an earlier refactor left their importers behind, which broke the production build outright.
- The landing page shows the current events. It was prerendered at build time, so its "upcoming events" list was a snapshot taken at deploy: a newly published event never appeared and a finished one never left, until someone redeployed. It now renders per request. This also removes the build's dependency on a reachable database, which is what was failing the Build and Lighthouse jobs.
- Facilitator, admin and super admin accounts no longer see the speaker bio and designation section. Those settings live on the speaker row, but the account settings hook and the profile endpoint both checked the role with a minimum-role test — which every role above speaker also passes. Both now require the exact speaker role.

### Added

- Event rooms show a session roadmap with a smooth progress bar. A sidebar on desktop tracks the event from start to finish: a vertical progress bar fills continuously based on event time, so two events of different lengths render the same bar — only the fill rate differs. Event start and end bookends frame the scheduled modules, which are marked done, live or up next. The roadmap draws its "live" mark from the same schedule rule as the LIVE pill, so the two can never disagree. Unscheduled modules have no place in time and are left off. Speaker names follow the same rule as the room cards, so a single assigned speaker stays unnamed.
- Event rooms call out the module running right now. While a module's scheduled slot is in session, the bar above the room shows a LIVE pill naming that module, and the module itself is highlighted in the agenda and tagged "Live now", so the whole room shares the same point in the schedule without reading ahead. When the event has more than one assigned speaker, the live module's speaker is named both in the bar and on the module; a single assigned speaker stays unnamed as redundant.
- Event rooms show each module's scheduled slot. Content modules and Q&A panels in the attendee, staff and speaker rooms display the module's time range and assigned speaker (e.g. "9:00 AM – 10:00 AM · Ada Lovelace") from the schedule the builder sets, so everyone in the session sees the same agenda without leaving the room. Modules without a schedule show nothing.
- Transactional email is actually delivered. Registration and check-in mail was written to the server console and never sent, so no attendee has ever received a ticket. Messages now go out from `no-reply@startuplab.center` through the organisation's own mail server, which the domain's existing SPF record already authorises — no DNS change was needed. The ticket QR travels as an inline attachment rather than a `data:` URI, which Gmail, Outlook desktop and Outlook.com all strip, and every message carries a plain-text alternative alongside the HTML. Delivery failures are recorded as a failed email-log row instead of breaking the registration that triggered them. Sending happens after the response rather than during it, so checking out and scanning a ticket at the kiosk no longer wait several seconds on a mail server.
- Event cover images can be uploaded from the staff event page. The upload endpoint already existed but had no caller anywhere, so a cover could not be set from the interface at all. Type and size are checked before the upload starts, against the same rules the endpoint enforces.
- Continuous integration. Four workflows run on every pull request: **CI** (format, lint, typecheck, unit tests with coverage, production build), **Security**, **Lighthouse**, and **E2E**. Each collapses into a single status check so branch protection needs no update when a job is added. The repository previously had no CI at all.
- Security scanning on every pull request and weekly on a schedule, so advisories against unchanged code still surface: CodeQL static analysis, gitleaks secret scanning over full history, a dependency audit that blocks on production advisories and reports dev-only ones, and a check that every table in a migration enables row level security.
- Lighthouse audits of the public routes (`/`, `/events`, `/sign-in`). Accessibility, best-practices, SEO and layout shift block on regression; performance and timing metrics warn, because they vary with CI runner load.
- **144 unit and integration tests** covering the request-handling trust boundary — the API routes, the session and role guards, the middleware's route protection, and DAO query shaping. Every route test asserts that an unauthorized request issues no database call at all, not merely that it returns 401.
- A sweep that reads all 43 API route files and fails if any lacks a `requireAuth` or `requireRole` call, so a route shipped without a guard breaks the build instead of shipping. Exceptions live in two explicit lists with written reasons.
- **41 end-to-end tests** driving a real browser against a real database: sign-in and route protection, the full purchase path from registration through ticket issuance to QR check-in, course material entitlement, event publishing, uploads read back through the entitlement gate, and course authoring. Each run provisions its own users, events and courses and deletes them afterwards, verified to leave the database exactly as it found it.
- Coverage measurement with thresholds set at measured values as a ratchet against regression. Statement coverage rose from 2.25% to 8.56%; the global figure stays low because components are most of the remaining surface, while the trust boundary itself is at or near full coverage.
- Dependabot, grouped so patch and minor updates arrive as one pull request and majors stay separate for review.
- Staff management pages for events, courses, emails, and organization under `src/app/staff/`.
- A dev-only browser profiler that surfaces client-side health while iterating. A provider in the root layout samples memory (`performance.memory` where Chromium offers it, `memoryUsage` elsewhere), live object and DOM counts, realtime channel usage, listeners and timers, plus a rolling average of how long each sample's metric collection took. Every sample prints one line to the `pnpm dev` terminal via a `console.log` sink that compiles to nothing in production, and `/staff/profiler` renders the same feed as cards with a heap sparkline, so a leak or listener churn can be caught while it is still tied to the tab that caused it. All of it is dead-code-eliminated from production builds: the provider is a no-op outside development, the route answers 404 unless `NODE_ENV` is development, and the instrumentation never runs off the client.

### Changed

- The landing page lists upcoming events as full cards — date, time, venue and cover art — instead of the bare title-and-date boxes it used to render, and the attendee home shows the same card grid at the same full-width spacing. The two pages previously drifted: the landing page hand-rolled its own minimal markup while the attendee home used the shared card component, and the home's cards ran edge-to-edge under the hero. Both now share one `EventGrid` so a change to the card design lands in a single place.
- General support is now a case queue. Every support session carries a global sequential case number — `CASE-10042` — shown in the attendee's chat header, and the staff inbox is a queue instead of an open floor: a case sits unclaimed until an admin claims it, and only the handler can reply, so two staff members can no longer answer the same attendee at once. The handler releases the case or ends it for good; the attendee starts a new one. Event support keeps its old immediate-reply flow, to be reworked separately.
- Course material is owned by the team running an event, not by whoever created the course. The `COURSE.created_by` column is gone — "who made this" still lives in the audit log's `course.created` event — and a course is managed by everyone assigned to its event: assigning a facilitator or speaker to the event is what grants authoring. Admins reach any course; deleting one is reserved for facilitators and admins, so an assigned speaker can still write material but cannot take the course down. Uploading course assets or videos used to need only the facilitator role, letting any facilitator write into any course, and the stored path was assembled from `course_id`/`module_id` the browser sent — which the builder was sending wrong anyway. Uploads now require an assignment to the lesson's event, and the path is derived from the lesson's own module and course ids with the client filename reduced to its basename, so neither the ids nor a path smuggled into the filename can redirect an upload outside its lesson. Flipping a Q&A lock is gated the same way, so an unassigned speaker can no longer freeze any module. The staff course authoring UI matches this policy: the admin courses table dropped its "Created By" column, since the column no longer exists, and the staff event page no longer offers a "Create Course" button to facilitators who are not assigned to that event — the button always failed with a 403 under the new policy. Authoring is shown only to the admin, the event's assigned facilitators, or its assigned speakers; everyone else sees the read-only course summary.
- Published event covers are served with a shared-cache lifetime, since they are the same bytes for every visitor and are rendered on pages anyone can read. Responses that depend on who is asking keep the `private` no-store header described above.
- Creating and editing an event share one form, so a field can no longer be added to one and forgotten in the other — which is how the two drifted apart.
- Uploaded images are compressed with WebAssembly instead of sharp. sharp binds to libvips as a native Node addon, which cannot load in the V8 isolate Cloudflare Workers runs, so it blocked deployment there outright. Uploads whose longest edge exceeds 1600px are now scaled to fit, which is invisible at the sizes the app displays — covers render around 350px wide — and is where most of the saving comes from: a 3200px camera JPEG drops from 393KB to 51KB, against 162KB for the quality change alone. JPEGs are still re-encoded at quality 80 on top of that. PNGs within the cap are stored as uploaded, since re-encoding one at its original size returns identical bytes; sharp used to quantise their palette instead. **Originals are not retained**, so a full-resolution upload cannot be recovered later.
- Migrated from Clerk to Supabase Auth. All auth logic centralized in `src/modules/auth/`.
- Old staff-related pages moved under `src/app/staff/` namespace; route protection updated accordingly.
- All API routes updated: `auth()` from Clerk replaced with `requireAuth()`/`requireRole()` from auth module.
- All client components updated: `useUser()`/`useClerk()` replaced with `useSession()` from auth module.
- Middleware rewritten to use `@supabase/ssr` for session management.
- Staff login page merged into unified sign-in page (role-based redirect).
- `pnpm test` now runs once and exits; `pnpm test:watch` is the watch mode. `AGENTS.md` asks contributors to run the tests before committing, which previously dropped them into a watcher.
- `prettier`, `vitest` and `eslint-config-prettier` moved out of `dependencies`. They were shipping to production, and separating them is what lets the audit block on production advisories while treating dev-only ones as advisory.
- `postcss` and `sharp` pinned above their advisories through pnpm overrides, clearing three high-severity findings that reached production through `next`.
