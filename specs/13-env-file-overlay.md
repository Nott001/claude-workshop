# 13 — Env files: local/remote overlay semantics

## Goal

Make the `.env` file a real overlay between two hosts instead of a file that
must be hand-edited on every switch. `node scripts/db-env.mjs local|remote`
rewrites a fixed block of keys and reports a redacted diff, and `.env.local` /
`.dev.vars` remain the live secrets layer Next.js and wrangler already read.

## Where

- `scripts/db-env.mjs` — `local`/`remote` modes, `REWRITE_KEYS`,
  `fetchLocalValues` (parses `supabase status -o env`), `readOverlay`
  (`.env.remote`), atomic write via tmp+rename, redacted diff printer.
- `.env.local` (gitignored) — Next.js overlays this over `.env`.
- `.dev.vars` (gitignored) — wrangler's SMTP/Mailpit stanza for `cf:preview`.
- `docs/DEPLOYMENT.md` — env-files table; `docs/LOCAL_DB.md` — dev SMTP path.

## Why

- Two rewrite warts existed before this: the `.env` was fully regenerated by
  one direnv-style mechanism while `NEXT_PUBLIC_*` inlining in the client
  bundle meant those lines must point at the _local_ stack for `pnpm dev`; and
  remote keys had to be hand-pasted. Splitting into "block the switch owns" +
  "block the human owns + dotenv overlay" is the smallest correct seam.
- Overlays are the idiomatic fit for Next/wrangler already: `.env.local`
  wins over `.env`, `.dev.vars` is wrangler-only. `db:env` touches only the
  four keys in `REWRITE_KEYS` so unrelated secrets (`SUPABASE_DB_PASSWORD`,
  `SMTP_*`, `PAYMENT_*`) survive both switches untouched.
- Atomic write (write tmp, rename) avoids a torn `.env` mid-switch.
- Failures are loud: `local` errors if `supabase status` didn't report the
  keys it needs; `remote` errors if `.env.remote` lacks any of the 4 required
  keys, so a switch never silently leaves hybrid endpoints.
- The diff is redacted (`…<redacted>` past column 18) so switching hosts in a
  team repo never prints a service-role key to the terminal.

## Steps

1. `.env.remote.example` documents the overlay; developer fills `.env.remote`.
2. `pnpm db:env local` → `fetchLocalValues()` runs `supabase status -o env`,
   maps `API_URL/ANON_KEY/SERVICE_ROLE_KEY` → the four keys, sets
   `NEXT_PUBLIC_APP_URL=http://localhost:3000`, rewrites `.env`, prints diff.
3. `pnpm db:env remote` → reads `.env.remote`, validates all 4 keys exist,
   rewrites `.env`, prints diff.
4. `.env.local` continues to override for per-machine tweaks; `.dev.vars`
   keeps `SMTP_*` for isolite previews.
5. `scripts/db-env.mjs` counts lines actually rewritten and refuses to run
   when fewer than `REWRITE_KEYS.length` matched (malformed `.env` guard).

## Verify

- `pnpm db:env local && pnpm db:env local` twice → second run prints "already
  in this mode" (idempotent).
- `pnpm db:env remote` with a complete `.env.remote` → the four keys flip and
  `SMTP_*`/`PAYMENT_*` stay byte-identical; with a missing key → exits 1 and
  names the missing key without touching `.env`.
